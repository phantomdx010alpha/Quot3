**Binding spec for Phases 51–60.** Sync is **optional and off by default**; Quot3 is fully functional with a single local database. This document is the design contract; Phase 51 turns it into SQL files under `supabase/sql/` and records them in `docs/SUPABASE_MIGRATIONS.md`.

Owner's requirement: *"supabase never stores bills data, it only acts as postbox for both"* and *"a simple license feature in the supabase for matching"*.

## 1. Principles
1. **Local SQLite is the source of truth** on every branch. History pages read only local data.
2. Supabase is a **transient encrypted mailbox**. It must never contain readable bill data (no party names, amounts, items). Metadata visible to the server is limited to: org id, sender branch, recipient branch, bill UUID, operation, revision, timestamps, ciphertext, nonce, size.
3. **No service_role key in the app.** The client uses only the anon key and calls **RPC functions** that validate the license.
4. Rows are deleted after the recipient acknowledges them; unacknowledged rows are swept after a TTL (default 30 days).
5. Last-write-wins on `updated_at`, tie-broken by `revision`, then by branch id; deletes are tombstones.
6. Sync never blocks the UI and never mutates a bill that is currently open in the editor (it raises a banner instead — see `UNDO_REDO_RULES.md` §2.7).

## 2. Identities
| Concept | Description |
|---|---|
| **License key** | Issued by the owner (generated manually in Supabase for now). One license = one organisation. Format `Q3-XXXX-XXXX-XXXX`. Stored hashed (SHA-256 + pepper-less salt per row) server-side. |
| **Organisation (`org_id`)** | UUID resolved from the license. |
| **Branch (`branch_id`)** | UUID generated by each installation when it joins; has a human name and a PO prefix (e.g. `BLR-`). |
| **Org passphrase** | Chosen by the owner when the first branch is created. Never sent to Supabase. Derives the encryption key (§4). Each new branch must be given it out-of-band. |

## 3. Supabase schema (to be written as SQL in Phase 51)

```
licenses(
  id uuid pk, org_id uuid unique, key_hash text unique, label text,
  kdf_salt bytea,   -- public per-org salt for the passphrase KDF (not secret)
  status text check in ('active','suspended'), max_branches int default 5,
  created_at timestamptz)

branches(
  branch_id uuid pk, org_id uuid references licenses(org_id),
  name text, po_prefix text, device_name text,
  registered_at timestamptz, last_seen_at timestamptz,
  unique(org_id, po_prefix))

postbox(
  id bigserial pk, org_id uuid, from_branch uuid, to_branch uuid,
  bill_id uuid, op text check in ('upsert','delete'), revision int,
  updated_at timestamptz, nonce bytea, ciphertext bytea,
  created_at timestamptz default now(), expires_at timestamptz)
  -- index (to_branch, id); index (expires_at)

sync_acks (optional audit; deleted with postbox row — not required v1)
```

**RLS:** enabled on all three tables with **no policies** for `anon`/`authenticated` — tables are unreachable directly. All access goes through `SECURITY DEFINER` RPCs that take the license key. (Same rule as the owner's other project: tighten RLS first, expose only RPC.)

### RPCs
| RPC | Input | Behaviour |
|---|---|---|
| `qt_register_branch(p_license, p_branch_id, p_name, p_po_prefix, p_device)` | | Validates license active and branch count ≤ max; rejects duplicate `po_prefix` within org; upserts the branch row; returns `{org_id, kdf_salt, branches:[{branch_id,name,po_prefix}]}`. |
| `qt_list_branches(p_license, p_branch_id)` | | Returns the org's branches (for the History branch filter and fan-out). |
| `qt_push(p_license, p_branch_id, p_items jsonb)` | array of `{to_branch, bill_id, op, revision, updated_at, nonce, ciphertext}` | Validates sender belongs to org and every `to_branch` is in the same org; inserts rows (max 200 per call, max 1 MB each); returns inserted ids. |
| `qt_pull(p_license, p_branch_id, p_after_id bigint, p_limit int)` | | Returns postbox rows addressed to this branch with `id > p_after_id`, ordered by id, limited. |
| `qt_ack(p_license, p_branch_id, p_ids bigint[])` | | Deletes those rows if they are addressed to this branch. |
| `qt_sweep()` | | Deletes rows past `expires_at`; scheduled (pg_cron or Edge Function). |
| `qt_touch(p_license, p_branch_id)` | | Updates `last_seen_at`. |

All RPCs: constant-time-ish license check, return a generic `invalid_license` error without leaking whether a key exists, and are rate-limited by Supabase defaults. A license key is typed once at activation and stored locally via `safeStorage`.

## 4. Encryption
- Algorithm: **AES-256-GCM**, 12-byte random nonce per message, the bill UUID + revision bound as **AAD** so ciphertexts cannot be swapped between bills.
- Key: derived from the **org passphrase** with **PBKDF2-HMAC-SHA256 (≥ 310 000 iterations)** and a per-org public salt stored in `licenses.kdf_salt` and returned by `qt_register_branch`. Derived key cached locally via `safeStorage` (Windows DPAPI); the passphrase itself is not stored.
- Payload = canonical JSON of the bill snapshot (header, party snapshot, format id, extra-column defs, rows, adjustment info, revision, updated_at, deleted flag), compressed (deflate) before encryption.
- If decryption fails (wrong passphrase / corruption) the row is **not acknowledged**, an error is logged and surfaced in Sync status; it is never silently dropped.
- Implemented with Node `crypto` in `src/main/sync/crypto.ts` (renderer never sees keys).

## 5. Local tables (SQLite; see `docs/DATA_MODEL.md`)
`sync_state(key, value)` — license (encrypted blob), org id, branch id, cursor `last_pulled_id`, enabled flag.
`sync_outbox(id, bill_id, op, revision, payload_hash, created_at, attempts, last_error, state)` — one row per pending change, created in the **same SQLite transaction** as the bill write (so a crash can't lose a change).
`bill.sync_state` column: `local_only | pending | synced | conflict`.

## 6. Flows
**Push:** outbox worker (every 15 s when online and enabled, and immediately after Save) → for each pending outbox row build snapshot → encrypt → `qt_push` to **every other branch** (fan-out: one postbox row per recipient) → mark synced on success; exponential backoff on failure (cap 10 min); poison rows (≥ 10 attempts) move to `failed` and show in Sync status.
**Pull:** worker (every 30 s, on app start, on network regain) → `qt_pull(after = last_pulled_id)` → decrypt → apply in one transaction per row (rules below) → advance cursor → `qt_ack`. The cursor advances only after a successful apply so a crash replays safely (apply is idempotent).
**Apply rules:** unknown bill → insert. Known bill → incoming wins iff `updated_at` newer, else if equal `revision` higher, else if equal branch id lexicographically greater (deterministic). Delete op → soft-delete tombstone with same ordering rule. A losing incoming change is dropped silently; when the local copy was *edited since last sync and also loses*, record `conflict` in `audit_log` so nothing is lost invisibly (the loser's snapshot is stored as a revision).
**Bootstrap (Phase 58):** a new branch gets history through a **backup import** (from another branch's backup file), then starts normal sync; it does not pull history from Supabase because the postbox is transient.
**PO numbers:** `po_number = branch.po_prefix + zero-padded per-branch sequence` (e.g. `BLR-0042`). Uniqueness across branches comes from the **unique prefix** enforced by `qt_register_branch`; the internal id is always the bill UUID. Changing a prefix later affects only newly created bills (existing PO numbers are immutable).

## 7. History page and branches
History shows bills from **this branch** by default and from **all branches** when sync is enabled and the filter is set to "All" (the data is already local after pulls). The PO prefix identifies the origin branch in the list.

## 8. What sync deliberately does NOT do (v1)
No live co-editing of the same bill; no party-list sync (parties are derived from bills and the local import — a later phase if the owner wants it); no server-side search; no attachments; no real-time websocket push (polling only — simple and robust).

## 9. Testing without a real Supabase (Phase 60)
`src/main/sync/transport.ts` is an interface with two implementations: `SupabaseTransport` and `InMemoryTransport` (used by Vitest and by the dev "two virtual branches" harness). All push/pull/apply/conflict/crypto behaviour is tested against `InMemoryTransport`; the SQL itself is run by the owner against a real project and results recorded as standing gaps until then.

## 10. Milestone 8 additions (Phases 87–89) — PLANNED

- **Parties on receive:** applying a remote bill links to an existing party by exact normalised name, else creates one (`source='sync'`); a one-time relink repairs older bills with `partyId = null`. (Gap found after Phase 68: received bills created no party and were not counted in Customers.)
- **Import to outbox:** imported legacy bills are enqueued in bulk in the same transaction batch; receivers dedupe by fingerprint / deterministic id, so a repeated delivery is ignored. Import on ONE branch only [A].
- **Progress:** send/receive progress events drive a progress bar. Needs a new server RPC `qt_pending_count` (SQL written in Phase 89, not run against a real Supabase = standing gap).
- **Wipe vs sync:** a wipe never sends deletes; other branches keep their data and may re-send it.
- **Version skew:** keep snapshot `v: 1`; new fields (`round_off`, footer extras, tail rows) are optional with defaults; old branches strip unknown fields, so update all branches.

## 11. Milestone 10 addition (Phase 111) — BUILT [A]
**As built:** payload `{ v: 1, kind: 'item_rule', rule, deleted }`; postbox `bill_id` = rule uuid, `revision` 0, AAD = (rule id, 0); `op` `delete` for a soft-deleted rule. Ordering: newer `updatedAt`, then greater branch id. A decision with the same content (fingerprint) as the local row is ignored even when newer, so the same decision on two branches stays one unchanged row. A rule that fails its checks is dropped and logged, never blocking the pipeline. A build WITH Phase 111 but without a rule applier acknowledges and ignores the kind; a build older than Phase 111 cannot read it and skips those rows after 10 runs (they stay unacknowledged until the TTL). Rules existing before sync was activated are not queued (a new branch gets them from a backup import). Wipe clears the outbox and never captures deletes; it does not touch `item_rules`.

**Original plan:**
New snapshot kind `item_rule` for the item sorter's remembered merges/splits: encrypted like bills, last-write-wins (`updated_at`, then revision, then branch id), deterministic id so identical decisions on two branches converge, optional for old branches (they ignore the kind). A wipe never sends deletes.
