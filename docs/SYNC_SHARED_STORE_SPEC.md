# SYNC_SHARED_STORE_SPEC — multi-branch sync through a shared Supabase notebook (Milestone 12)

**Binding spec for Phases 128–143.** It REPLACES the encrypted-postbox model of `docs/SYNC_POSTBOX_SPEC.md`. That older spec stays binding until Phase 140 (cutover) is done and Phase 142 (retire v1) has removed the old code; after that it is history. Sync is still **optional and off by default**; Quot3 is fully usable with one local database. Design context and the owner's decisions: `docs/MILESTONE12_DESIGN.md`. **[A]** = planner assumption the owner may flip.

Owner's words (2026-10-12): *the latest version wins, it does not matter which branch it comes from*; *a simple generated license plus Supabase email and password for main and branches*; *branch names selectable to avoid conflict*; *license generation by one simple Supabase SQL query that also creates the Supabase email and password*; *no passphrase*; *old imported bills should reach the other computer without backup-file swapping*; *customers with the same name must not duplicate*.

---

## 1. Principles
1. **Local SQLite is still the working copy** on every branch. The app writes SQLite first; sync is a background step. History, Customers, Items read only local data.
2. **Supabase is a durable shared notebook** (the server remembers every record and every tombstone). It is NOT encrypted by us. Readable bill data (party names, phones, amounts, items) now lives on the server. See section 11 for the accepted risk.
3. **No passphrase, no encryption layer.** Access control = Supabase Auth (email + password) + Row Level Security + a license key. Therefore the "could not be read / decrypt pause" failure of v1 cannot occur.
4. **All branches are equal.** No Main / Branch role. Roles, read-only branches and "main wins" were proposed and rejected/not requested.
5. **No `service_role` key in the app.** The client holds the URL + public anon key and a user session. Writes go only through `SECURITY DEFINER` RPCs (they enforce versioning); reads of own-organisation rows are allowed by RLS (needed by Realtime).
6. Sync never blocks the UI and never mutates a bill that is open in the editor (banner, as Phase 56).
7. Never lose data silently: a losing version is kept (server history + local revision).

## 2. What changes from v1
| Topic | v1 (Phases 51-60) | M12 |
|---|---|---|
| Server role | transient mailbox, rows deleted after ack | durable store, latest version of every record, nothing deleted by sync |
| Data on server | AES-256-GCM ciphertext | plain `jsonb` (RLS-protected) |
| Join later | impossible; backup-file swap | pull everything from sequence 0 (paged) |
| Identity | license key + org passphrase | license key + Supabase email/password (one login per branch seat) |
| Conflict | client clocks, revision, branch id | server version chain; ties by skew-corrected `edited_at` (section 6) |
| Delivery | 30 s poll | Realtime "doorbell" + 60 s poll backup |
| Customers | derived from bills, duplicates on merge | synced records, exact-name auto-merge, similar names -> manual Merge list |
| Old app meets new data | strips unknown fields | sets the record aside, shows "Update the app to see N bills" |

## 3. Identities
| Concept | Description |
|---|---|
| **License key** | `Q3-XXXX-XXXX-XXXX` (same alphabet as v1), generated by the SQL function in section 5, stored only as `sha256('quot3-license:' + KEY)` in `public.licenses` (table reused). One license = one organisation (`org_id`). |
| **Seat** | One Supabase Auth login (email + password) per computer, created together with the license. Number of seats = `licenses.max_branches` (default 5). A seat belongs to one organisation (`sn_members`). |
| **Branch** | One installation: `branch_id` uuid made by the app, a human **name** (chosen in Settings, unique per organisation, case- and space-insensitive) and a **PO prefix** (unique per organisation, same alphabet as before). A seat is bound to one branch id at a time. |

## 4. Server schema (SQL files `supabase/sql/11_*.sql` onward; v1 files 01-06 are NOT edited)
```
public.licenses            -- reused: org_id, key_hash, label, status, max_branches (kdf_salt stays, unused)
sn_members(user_id uuid pk -> auth.users, org_id, seat_no int, branch_id uuid null, created_at)
           unique(org_id, seat_no)
sn_branches(branch_id uuid pk, org_id, user_id, name, name_norm, po_prefix, device_name,
            registered_at, last_seen_at, unique(org_id, name_norm), unique(org_id, po_prefix))
sn_records(org_id, kind text check in ('bill','party','party_merge','item_rule'), rec_id uuid,
           version int, server_seq bigint, deleted bool, payload jsonb, payload_hash text,
           schema_ver int, min_reader_ver int, app_ver text, edited_at timestamptz,
           from_branch uuid, updated_at timestamptz default now(),
           primary key (org_id, kind, rec_id))   -- index (org_id, server_seq)
sn_history(id bigserial, org_id, kind, rec_id, version, payload jsonb, from_branch, edited_at,
           replaced_at, reason text check in ('superseded','conflict_loser'))   -- capped per record (20) by the RPC
sn_ping(org_id uuid pk, seq bigint, at timestamptz)   -- one tiny row per org; the Realtime doorbell
```
`server_seq` comes from one database sequence (monotonic, gaps allowed). `payload` is at most 1 MB per record (enforced). The old `branches` / `postbox` tables are left alone and dropped by an owner-run script in Phase 142.

## 5. Accounts, license and the one-query generator (Phase 129)
**Owner requirement:** creating a license must be one simple SQL query in the Supabase SQL editor, and it must also create the Supabase email + password for each computer.

```sql
select * from public.qt_create_org('Acme Traders', 3);
-- optional: your own emails instead of generated ones
select * from public.qt_create_org('Acme Traders', 3, array['blr@acme.in','mys@acme.in','hub@acme.in']);
```
Returns one row per seat: `license_key` (same on every row), `seat_no`, `email`, `password`. **It is shown once**: the key is stored only hashed, passwords only as bcrypt in `auth.users`.
- Default emails are generated (`<slug>-<seat>@<domain>`; the domain is a parameter with a default) and are created already confirmed, so no mail is ever sent (password reset by mail therefore does not work; use `qt_reset_seat`). [A] Phase 129 must check on a real project that Supabase accepts the generated domain.
- Passwords: 16 characters from an alphabet without look-alike characters, from `gen_random_bytes`.
- Mechanism [A]: the function inserts into `auth.users` and `auth.identities` directly (the usual SQL-editor technique; token columns set to `''`, not NULL, provider `email`, `email_confirmed_at` now, bcrypt via `extensions.crypt`). This touches Supabase-internal tables, so it is **not proven until the owner runs it** (standing gap). **Fallback documented in `SUPABASE_MIGRATIONS.md`:** create the logins in Dashboard -> Authentication -> Users (auto-confirm), then `select public.qt_attach_seat('Acme Traders', 'user@email')`.
- Helpers (all owner-only, not executable by `anon` / `authenticated`): `qt_add_seats(label, n)`, `qt_reset_seat(label, seat_no)` (new password, shown once), `qt_revoke_seat(label, seat_no)`, `qt_set_license_status(label, 'active'|'suspended')`, `qt_attach_seat(label, email)`.
- **Hard setting for the owner:** Authentication -> Providers -> Email: **disable "Allow new users to sign up"**. Even if it is left on, a stranger's account has no `sn_members` row and sees nothing (RLS), but disabling it is the first line of defence. The self-test cannot check this setting; the checklist does.
- The license key that was pasted into a chat during the v1 debugging is retired (the v1 license row is suspended in Phase 140). Never put a license key, password or anon-key-with-service-role in the repo.

## 6. Records, versions and "latest wins" (Phases 130, 134, 135)
Every synced thing is a **record** `(kind, rec_id)`: a bill, a party (customer), a party merge decision, an item rule. Each has a server-assigned `version` (1, 2, 3, ...) and `server_seq`.

**Push** `sn_push(p_license, p_branch_id, p_items jsonb)`, 1-200 items, each `{ kind, rec_id, base_version, payload, payload_hash, schema_ver, min_reader_ver, app_ver, edited_at, deleted }`. `base_version` is the version the sender had last seen (0 = new). Server rule, per item, in one transaction:
| Case | Result |
|---|---|
| no row yet | insert, version 1, outcome `accepted` |
| `payload_hash` equals the stored hash | nothing written, outcome `noop` (idempotent resend) |
| `base_version` = stored version | accept; the old row goes to `sn_history` (`superseded`); version + 1; outcome `accepted` |
| `base_version` < stored version (both sides changed) | **conflict: the later `edited_at` wins**; ties go to the greater `branch_id`. The loser's payload goes to `sn_history` (`conflict_loser`). Stored version is still +1. Outcome `won` or `lost`. |
Each write takes a new `server_seq` and touches `sn_ping` once per push call (not per item).

**What "latest" means.** `edited_at` is the sender's clock corrected by the offset it measured against `sn_now()` at its last contact (so a wrong Windows clock does not decide a conflict). The server never uses `edited_at` for ordering the pull, only for deciding a conflict. If the measured offset is over 2 minutes the app shows a quiet warning. [A] This keeps the owner's rule ("whichever is latest wins, any branch") without trusting raw clocks. A `lost` outcome makes the client store its own version as a local revision (History -> compare) so nothing is lost.

**Pull** `sn_pull(p_license, p_branch_id, p_after_seq, p_limit)` returns changed records with `server_seq > p_after_seq`, ordered, at most 200 rows / about 4 MB, plus `has_more` and `server_time`. Pulling deletes nothing. A new branch starts at 0 and receives the whole notebook, paged. Tombstones (`deleted = true`) are kept forever [A].

## 7. The diff matcher (Phase 134, pure `shared/sync/diff.ts`)
Used for the **first sync** of a computer and after a long offline spell. `sn_manifest(p_license, p_branch_id, p_kind, p_after_rec_id, p_limit)` returns a light list `(rec_id, version, payload_hash, server_seq, deleted)` (up to 1000 per page). The client builds its own list from SQLite (`rec_id, hash, base_version`) and `planSync(local, remote)` returns buckets:
| Local vs server | Plan |
|---|---|
| same id, same content hash | **skip** (record `base_version`) |
| only local has it | **upload** |
| only server has it | **download** |
| both, differ; local unchanged since `base_version` | download |
| both, differ; server still at local `base_version` | upload |
| both, differ; both changed (or no base known) | **conflict** -> later `edited_at` wins, loser kept as revision |
Content hash = hash of the canonical sync fields, the same notion as `sameContent` / the legacy-import fingerprint (not `revision`, not `updated_at`). Legacy-imported bills therefore need no special path: import on ONE computer, press Sync, they are "only local" so they upload; the other computer downloads them. Bills that both computers already hold with the same id and content (the 1 927 merged through a backup) are skipped.

## 8. Snapshot format and version stamp (Phase 133)
Payload is plain canonical JSON `{ v: 2, kind, ... }` (no encryption, no deflate). Every record carries `schema_ver` (what wrote it), `min_reader_ver` (oldest reader that can handle all fields without loss) and `app_ver` (display only).
- A reader with `reader_ver >= min_reader_ver` applies it. Unknown OPTIONAL fields are preserved in `unknown_json` and written back on push (an older app must not drop a newer field).
- A reader with `reader_ver < min_reader_ver` does **not** apply or overwrite it: the record goes to local `sync_aside`, the cursor still advances, and the UI shows "Update the app to see N bills". After an update, `retryAside()` applies them. A local edit of an aside record is blocked.
- A new bill format or extra column needs **no server change**: it is new content in `payload`. A server change is only needed for a new `kind` (the column is text with a check list; adding a kind is one small SQL file).

## 9. Customers (Phase 137)
- Parties become records of kind `party`. The record id is **deterministic from the normalised name** (uuid from `org_id|name_norm`), so two branches that both create "SPACE GARMENTS" produce the SAME record: exact same name = automatically one customer.
- Existing local parties have random ids. A one-time **unify** step (idempotent, with undo) groups by normalised name, keeps the one with most bills (tie: oldest), re-points `bills.party_id`, soft-deletes the others and emits `party_merge` records so other branches do the same. The owner's 12 893 customers are the test corpus (counts only, no contents in tests or logs).
- **Similar** (not equal) names, e.g. "Space Garment" vs "Space Garments Ltd", are never merged automatically. They appear in Customers -> "Possible duplicates" with a **Merge** button (and Not the same). A merge is a `party_merge` record (survivor id, merged id, who/when), synced and applied everywhere, with undo of the last merge. The survivor keeps its own phone / address; blanks are filled from the merged one.
- Numbers, sizes and units rules of the item sorter do not apply here; party similarity uses the existing party fuzzy search plus token rules, deterministic and explainable. [A]

## 10. Realtime doorbell (Phase 138)
Supabase Realtime `postgres_changes` on `sn_ping` filtered to the organisation. The event carries no data. On an event the main process runs the normal pull (debounced 500 ms). A **60 s poll** always runs as backup, and a pull also runs at start, after Save, and on network regain. Realtime is created and held only in the main process (the renderer has no network, CSP unchanged). If Realtime fails, the app silently keeps polling. A bulk import or the customer unify sends one push call, so one ping.
**Realtime limits, re-read in Phase 138 (2026-10-13) from Supabase's own page `supabase.com/docs/guides/realtime/limits`, Free plan:** 200 concurrent connections, 100 messages per second, 100 channel joins per second, 100 channels per connection, 256 KB broadcast payload. Beyond the limit a join is refused (`too_many_connections` / `too_many_joins`) or, for message rate, clients are disconnected and `supabase-js` reconnects when the rate drops. That page states NO monthly message allowance: the earlier "about 2 million messages a month" came from third-party pages and is NOT confirmed (the pricing page was not read). Two computers use two connections, one channel each, and one tiny message per push: far inside every limit. [A]

**As built (Phase 138):** `shared/sync/pull.ts` holds the numbers (`SHARED_POLL_MS` 60 s, `DOORBELL_DEBOUNCE_MS` 500 ms, reconnect 2 s doubling to 5 min, `deliveryText`); `main/sync/doorbell.ts` `createDoorbell` subscribes through `transport.subscribeDoorbell`, turns a burst of rings into one `pull.kick()` after 500 ms, reconnects with backoff when the socket drops or cannot be made, and kicks once whenever it becomes live again (rings may have been missed). The 60 s poll is the pull worker's own timer (`pollMs: SHARED_POLL_MS`, default stays 30 s for the v1 worker) and always runs. `SyncOverview.delivery` / `deliveryText` carry "Live" or "Checking every minute". Not wired into `main/index.ts` until Phase 140 (it passes `pollMs`, starts the doorbell after sign-in, stops it on sign-out, and calls `notifyOnline` on network regain).

## 11. Security and accepted risks
- Tables `sn_*` have RLS on. `anon` has no access at all. `authenticated` may only `select` rows of its own organisation (join through `sn_members`); there is NO insert / update / delete policy; every write is an RPC with an empty `search_path` that reads `auth.uid()`, checks membership and the license, and enforces size limits (200 items, 1 MB per payload, 8 MB per push, 1000 per manifest page).
- RPCs return the same generic errors for bad key / unknown / suspended license (`Q3L01`). New codes: `Q3A01 not_member`, `Q3B04 name_taken`, `Q3B05 seat_in_use`, `Q3R01 payload_too_large`. Client-only: `AUTH_FAILED`, `SERVER_PAUSED`.
- **Accepted risk (owner to confirm):** readable bill and customer data, including real names and phone numbers from the legacy import, is stored on Supabase. It is protected by TLS, a generated password per seat, RLS, disabled sign-ups and a license key; it is not protected from someone who controls the Supabase project itself (the owner). Windows BitLocker on the PCs is still recommended.
- Client: the session (refresh token) and the seat password are kept in `sync_state` wrapped by Electron `safeStorage`; sync activation is refused when `safeStorage` is unavailable; the renderer never receives the key, password, anon key or tokens (`license:status` returns masked hints only); logs and audit rows never contain them. HTTPS only.
- **Free plan facts that matter:** projects pause after about 7 days without activity (the app must show "sync server paused or unreachable", not "no internet"; the owner clicks Restore in the dashboard); the Free plan has no automatic backups, so local backups stay the safety net and the cutover (Phase 140) forces a fresh backup first. [A] verify both on the live plan page.

## 12. Client contract (details in `API_CONTRACTS.md`, M12 section)
`src/main/sync/sharedTransport.ts`: interface `SharedStoreTransport { signIn, activate, branchNameFree, listBranches, now, manifest, push, pull, subscribeDoorbell }` with `InMemorySharedTransport` (tests, dev harness; mirrors the RPC rules above) and `SupabaseSharedTransport` (the only code importing `@supabase/supabase-js`). `supabase-js` already contains Realtime; no new package is planned. The outbox (`sync_outbox`) is reused for change capture; the pull cursor becomes `server_seq`; per-record `base_version` lives in a new local table (`DATA_MODEL.md`, M12 section).

## 13. Testing without a real Supabase
Everything is tested against `InMemorySharedTransport` (push rules, conflicts, diff plans, aside rule, customers unify, doorbell fallback, N-branch convergence with a lossy wrapper). The SQL is covered by a static test (`src/__tests__/supabaseSql.test.ts` extended) and `supabase/sql/91_selftest_v2.sql` (ends in ROLLBACK). **Nothing here is "verified against Supabase" until the owner runs the checklist in `SUPABASE_MIGRATIONS.md`.** Never run against a real Supabase from the sandbox.

## 14. Deliberately NOT in M12
No Main / Branch roles; no read-only branch; no live co-editing of one bill; no end-to-end encryption; no server-side search; no attachments; no automatic server backups; no pg_cron sweep (nothing expires). Wipe ("Start fresh") never sends deletes and never touches the server.

## 15. The v1 decrypt bug
The 2026-10-12 handoff recorded a decrypt pause between two computers whose root cause was never confirmed (candidates: different passphrases, leftover rows, an AAD / revision sealing bug). M12 removes the code path instead of diagnosing it. If the owner still wants the cause, the handoff steps (fingerprint compare, failing-row reason) remain valid for the v1 build only.
